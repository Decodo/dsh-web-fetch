Phase 0 results, dsh 0.1.2-rc.1 (npm latest, 2026-09-07), plugin at commit TBD in the private repo. Go / no-go: GO.

Gate 1, install and activation: PASS. `dsh plugin add <package>` into a fresh headless profile inserted the bundle layer; `--dump-config` shows tool-web `fetch: true`, `fetchTimeoutMs: 60000`, web `fetchProvider: decodo`, and the `web-fetch-decodo` row. Profile cordis.patch.yml untouched. Note: 0.1.2-rc.1 base already mounts an official `http` fetch provider with fetch enabled (the spec page said fetch was disabled with no provider), so the explicit `fetchProvider: decodo` pin is what makes ours win, not sole-provider auto-select. Also: a patch replaces a row's whole config, so the bundle restates `searchProvider` and `searchTimeoutMs`.

Gate 2, success vs direct API call: PASS, 100% in both runs. 20 URLs (10 answered a plain curl with 403/429, 10 answered 200). URL set in phase0/urls.json. Run A: direct 18/20, dsh 18/18 of those. Run B: direct 17/20, dsh 17/17 of those (dsh also succeeded on one URL where the direct call got a target 401 that run). The two consistent non-successes are API-side and identical in both paths: ticketmaster.com gives HTTP 400 "Url is not supported." from the API; yelp.com returns a target 403 "enable JS" body through the API. Neither is plugin-caused. Zero markdown-conversion fallbacks.

Gate 3, added latency and timeouts: PASS. Median dsh-minus-direct: run A (direct first) -297 ms, run B (dsh first) -11 ms; the sign flips with order, so the true overhead is within noise of zero. Zero dsh-side timeouts in 40 fetches (60 s budget); zero where the direct call finished within 20 s. Absolute latency, info only:
- protected: direct p50 2.9 s / p95 14.3 s (A), 3.2 s / 8.1 s (B); dsh p50 2.6 s / p95 5.5 s (A), 2.7 s / 11.4 s (B)
- plain: direct p50 2.4 s / p95 6.0 s (A), 1.7 s / 5.9 s (B); dsh p50 1.5 s / p95 4.9 s (A), 1.7 s / 19.4 s (B, one gnu.org outlier)
Method: a throwaway plugin inserted with a `--patch` overlay disables the headless agent runner and calls `ctx.web.fetch` (the exact seam call web_fetch makes) under `AbortSignal.timeout(60000)`, then renders with dsh-tool-web's `formatFetchOutput`. No model in the loop (no DeepSeek key available here), so model latency is excluded, everything from profile boot through provider and tool rendering is included. Direct call is the same POST /v2/scrape with `markdown: true` from the same process. Raw rows in phase0/results/run-a.json and run-b.json. Additionally confirmed with a model in the loop (Claude Sonnet 4.6 via the Nexos gateway, headless profile): the agent's own web_fetch on zillow.com returned HTTP 200 with the page heading through Decodo, and with the token unset the model saw only the provider-unavailable error.

Gate 4, missing token: PASS, no silent fallback. Token unset: `available()` is false, the seam throws `WEB_PROVIDER_CONFIGURED_UNAVAILABLE` "configured web provider "decodo" is registered but unavailable" in 5 ms; the mounted `http` provider is not used. Wrong token: `DECODO_AUTH_FAILED` "Decodo authentication failed (HTTP 401): Incorrect username or password. Check the Web Scraping API token". Open point for review: with the spec's env-presence `available()`, the unset-token message comes from the seam and does not name SCRAPER_API_TOKEN; returning `available: true` and throwing from fetch() would give the model the named-variable message instead.

Analytics header: the plugin sends `x-integration: dsh`, the convention the CLI (`cli`), MCP (`mcp`) and OpenClaw (`openclaw`) use. scraper-api maps unknown values to plain API traffic (ScrapingParameterContextHandler.STRING_TO_INTEGRATION_METHOD), so a small scraper-api change adding `dsh` to INTEGRATION_METHOD and that map is needed before plugin traffic is distinguishable. Separate MR, not in this repo.
